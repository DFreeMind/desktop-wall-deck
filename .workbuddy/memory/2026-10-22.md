# 2026-10-22

## 桌面壁纸应用（desktop-wall-deck）从零落地

用户要求：调研 + 开发一个 Windows 多显示器壁纸应用，支持选屏设置、全部统一、本地壁纸库管理。
要求 git 管理、写 AGENTS.md、在分支开发、中文提交注释。

### 关键决策与依据

- **技术栈选 Tauri 2 + Rust + React**，排除 WPF 的原因是本机只有 .NET SDK 2.1.700，
  `dotnet build` 对 net8.0-windows 直接报 NETSDK1013，装不了新 SDK 就跑不起来。
  Rust MSVC 1.96 + Node 22 是现成可用的。
- **COM 线程模型**：`IDesktopWallpaper` 是 STA 对象，全部调用收敛到单一 worker 线程
  （`wallpaper/com.rs` 的 `WallpaperWorker`），主线程通过 channel 请求。结构性避免跨线程传指针。
- **显示器身份用 EDID 派生**（厂商码+型号+UID），不用 device path，因为换 HDMI 口路径会变。
- **跨屏拼接本地切图**，不用 `SetPosition(SPAN)`：副屏纵向偏移时 SPAN 会露黑边。

### 踩过的坑（均已在代码注释中记录原因）

1. `windows` crate 0.58 的 `RegisterClassW` / `WNDCLASSW` 被 `Win32_Graphics_Gdi` feature 门控，
   要显式加这个 feature 才能创建隐藏窗口收 `WM_DISPLAYCHANGE`。
2. `CreateWindowExW` 的 hinstance 参数是泛型 `P4: Param<HINSTANCE>`，传 `Some(h)` 编译不过，要传裸 `HINSTANCE`。
3. `GetModuleHandleW` 返回 `HMODULE`，转 `HINSTANCE` 要显式 `HINSTANCE(h.0)`。
4. 虚拟屏识别特征词曾写成 `"root\\"`，但设备路径分段符是 `#`（实际文本 `ROOT#DISPLAY`），
   导致漏判——单元测试抓到，改为 `"root#"`。
5. Tauri 构建必须要有 `src-tauri/icons/icon.ico`，否则 build.rs 直接失败。

### 一个重要的设计纠错

初版把壁纸统一转 PNG 求「无损」，实测很糟：3 张真实壁纸 PNG 后 12.9MB（原图 10.05MB 的 128%），
最大一张 2520×2100 达 8.8MB。改为 JPEG 质量 92 后只有 2.09MB（21%），屏幕上看不出差别。
带 alpha 的图仍走 PNG。测试里加了体积回归断言防倒退。

### 验证情况

- 10 个单元测试全过（身份解析、虚拟屏识别、比例提示、库导入去重删除）
- 2 个集成测试全过：真实图片导入（体积 21%）、真实投放并回读一致后恢复原状
- release 可执行文件 9.4MB，能正常启动建库

## 第二轮：设计稿对齐 + 文件夹管理

用户拿到两张设计图截图，指出还原度差距大，同时提 4 项新需求：文件夹管理（含穿透）、
开源壁纸站入口、未分配屏预览、右栏视觉优化。

### 后端：文件夹（合集）

- `folders` 表自引用 `parent_id`，带 `ON DELETE CASCADE`；`wallpapers` 增量加 `folder_id` 列
- 迁移用 `PRAGMA table_info` 探测列是否存在，再决定 `ALTER TABLE`，兼容已存在的旧库
- **删除语义是这次最关键的设计判断**：合集是分类标签而非容器，删合集不能连带删图。
  事务内先把壁纸挂到父级（顶级则 `NULL`）、子文件夹上移一级，最后才删该行
- `folder_tree` 一次查询返回全树，`total_count` 自底向上累加，避免前端 N 次请求

### 前端：三栏重构

- 196px 导航 + 内容区 + 288px 右栏，替代原来的上下结构
- 新增 icons.tsx（20 个自绘线性图标）与 dialogs.tsx，不引任何 UI / 图标库

### 这轮踩的坑

1. **缩略图全灰、`naturalWidth === 0`、控制台零报错**：`assetUrl` 无脑把输入拼到
   `http://asset.localhost/` 后面，base64 的 mock 图被编码成 `data%3Aimage/png...`。
   修复是在编码前放行 `data:` / `blob:` / `http(s):` 前缀。这类静默失败最难往编码上想。
2. **画布只有 210px 高、显示器缩成小方块**：原按 `(availW/bw)*bh` 等比适配宽度，
   三屏横排包围盒极扁（宽很多、高很少），算出来高度很小。改为以「最矮的屏 ≥ 130px」
   反推画布高度，再和上下限夹逼。配套要加文字降级阈值（168/118），否则屏名和「未设置」重叠。
3. **卡片「更多」按钮点不到**：`opacity: 0` 会被可访问性判定为不可见，
   Playwright 直接 actionability 超时，真机触屏也唤不出。改基线 `0.42` + hover/focus 提到 1。
4. **WebView2 在沙箱下彻底不可用**：debug 版崩 CrashSender，release 版窗口存活但渲染空白。
   尝试过移除顶栏 `-webkit-app-region: drag`，无效。最终放弃原生截图，改 Playwright + 打桩 harness。

### 验证方案的转折

原生截图路走不通后，没有再写一个独立的预览页（那样验的就不是真界面了），
而是给 `window.__TAURI_INTERNALS__.invoke` 打桩，让浏览器渲染**同一份** `App` 组件——
样式和布局与真实界面完全共用。这套 harness 已进 `.gitignore`，属本地调试工具。

Playwright 断言结果：全部 8 张 / 点「自然风景」4 张（2 本层 + 2 子集穿透）/ 「高山」2 张 /
未归类 2 张 / 新建合集自动跳转 / 移动弹窗计数与「当前位置」标记正确 / console 无报错。

## 第四轮：修 6 项问题（提交 1553e46）

用户要求逐项排查修复，约束是「不改原有功能逻辑、不引入未提及技术栈」，
且界面改动无需截图比对走查。

### 三个真根因（都不是表面现象）

1. **当前壁纸预览空白**：系统壁纸在 `%APPDATA%\Microsoft\Windows\Themes\TranscodedWallpaper`，
   **无扩展名**且不在 asset scope 内，WebView 猜不出 MIME → 静默失败。
   解法是后端解码成 data URL（`make_preview_data_url`，缩到 480）。刻意**不放宽 scope**，
   放宽到 `$APPDATA\Microsoft` 等于把系统主题目录暴露给前端。
2. **更多菜单被裁**：菜单在 `overflow: hidden` 容器内，裁切发生在绘制阶段、早于 z-index
   层叠比较——所以调多大 z-index 都没用。必须 Portal + fixed。
3. **缩略图糊**：`image` crate 的 `thumbnail()` 是 area 采样，高对比边缘发糊。换
   `resize(..., Lanczos3)` 且原图小于目标时不放大，THUMB_EDGE 440→640。

另一个隐性缺陷：卡片和右栏都用了 `assetUrl(filePath)`（原图，可能几 MB），
应为 `assetUrl(thumbPath)`。这是瀑布流卡顿 + 显示不全的常见成因。

### 新增能力的边界

- 文件夹导入是**复制**进库（沿用「不引用原路径」原则），源目录不自动同步。
- 壁纸来源改 iframe 内嵌，但能否嵌入由对方 `X-Frame-Options` 决定，Pexels 明确拒绝。
  因此 `embeddable` 字段 + `.browser-blocked` 说明 + 外链兜底，不能白屏。
  跨域 iframe 的 `onLoad` 不可靠，遮罩必须带定时兜底（4.5s）。
- 考虑过 `add_child` 原生子 WebView，需要 Tauri `unstable` feature，属引入新东西，未采用。
